# ZL Dev Roadmap

本路线图安排后续工作，未指定发布日期、工时或 token 节省比例。0.16.1 已完成按需报告策略与 go 延后渲染的兼容路径；0.17.0 已加入会话关联及续作定位。0.17.1 已加入 task/feature 快照发布保护；0.19.1 已完成当前提示词统一，成本基线仍按 TODO 状态推进，不宣称全部路线已完成。逐项验收条件见 [TODO.md](TODO.md)。

## 目标

让一个或多个会话可以明确地推进不同任务或协作同一任务，同时只在有阅读、决策或交接价值时生成 HTML。任务保留长期事实，报告保留适用版本，普通交流保持轻量。

```text
R0 明确产出与定位契约
  → R1 轻量续作、会话关联与报告一致性
  → R2 专用分析流程和执行上下文
  → R3 按实测成本进一步优化
```

## R0：先把默认行为说清楚

历史边界：早期未采集完整的改动前成本原样本。0.21.0 从固定旧代码回放建立初始对照，不等于恢复旧版本发布当时的消费或账单。

**范围：ZL-01、ZL-03 的定位契约，ZL-06 的冲突清单，ZL-11 的改动前基线准备。**

- 在 R1 改动前固定 0.16.0 对照场景并记录可获取的 usage、工具量和报告次数；无法取得的指标标未知，保留以后可复跑的基线。
- 明确三种独立产出：对话回复、必要事实保存、HTML 审阅材料。阶段是工作组织方式，不是每轮生成文件或审批的开关。
- 明确续作优先级、会话缺失时的消歧规则及多任务切换语义。保存跨会话任务，不引入全局“当前任务”。
- 统一检查执行、结果接受与行动授权；确认旧文档中的强制人工/批量生成要求应移除或改写的位置。
- 将只分析、只审查、开发、受托验收、运维及交接场景映射到有限的产出策略，不再靠通用“最终必须给 HTML”覆盖全部情况。

**退出条件：** TODO 中报告策略表与多会话场景能得出唯一、可解释的默认行为；未形成事实的问答无需新建任务或报告；没有新的用户操作命令、人工签字或权限要求。

## R1：先解决日常最容易遇到的重复与竞争

进展：ZL-02～06 已落实，最新指引按入口和当前动作加载，保留真实模型不遵循时的评测限制。

**范围：ZL-02、ZL-03、ZL-04、ZL-05、ZL-06。依赖 R0。**

- 新入口的创建/恢复与报告生成解耦；旧 `init/continue` 返回值采用兼容迁移（可选 defer/no-render 或独立内部接口），不直接破坏现有客户端与老任务。
- `go/status` 使用明确任务关联；支持会话切换、接手和没有可靠宿主 ID 时的显式引用回退。
- 阻止旧快照晚写覆盖当前报告；同时覆盖 task 与 feature 页面。
- 清理逐动作 `render/index`、逐子动作 `sync/render` 功能总览和全量资料加载要求；必要事实继续及时保存，`status` 继续只读。

**退出条件：** 同项目 A/B 会话分别继续各自任务；普通追问和状态查询不重生页面；旧快照竞争不退回当前报告；CAS、版本、失败及旧证据保护仍有效。用真实 Claude Code 做限定插件流程验证，记录加载来源与实际结果，不扩展业务测试网站。

## R2：支持真实任务类型与执行位置

进展：0.18.0 已完成 ZL-07 的只读分析分支及专用报告；ZL-08～11 仍按 TODO 推进，0.19.0 已增加本机 checkout 身份和协作活动检测；ZL-09 仍仅部分完成，未实现执行隔离、跨机器映射或证据迁移。0.20.0 已完成 ZL-10 同版报告复用及独立模板时效，0.21.0 已补 ZL-11 采样工具与三组单样本初始回放；R2 剩余为 ZL-09 未完成部分、成本重复样本与归因，不宣称整个阶段完成。

**范围：ZL-07、ZL-08、ZL-09、ZL-10、ZL-11。依赖 R1；分析流程与工作区设计可在契约稳定后独立推进。**

- 补业务逻辑与数据链路的只读流程、记录与专用展示，不要求其进入开发和验收。
- 分开逻辑项目、长期任务、会话关联、工作区与执行证据。为共享 checkout 的活动写任务提供明确信息，按实际冲突选择分工、串行或独立 worktree。
- 对同仓多 worktree、跨机器和跨工具接手采用显式关联，保留旧存储兼容，禁止静默迁移与证据改绑。
- 有效内容和模板均无变化时复用已有报告；变化时如实标记旧快照，按阅读需求重生。
- 建立成本基线，区分模型 usage、读取内容、完整 JSON 传输、工具返回、渲染次数和实际验证耗时。

**退出条件：** TODO 的只读分析、共享工作区、worktree/跨工具、模板时效场景通过；报告能讲清实际执行上下文；成本报告使用实测数据，不把少调用几次 render 等同于 token 同比例下降。

## R3：只做数据支持的进一步优化

**范围：ZL-12、ZL-13、ZL-14。依赖 R2 的上下文模型和成本基线。**

- 若全量事实传输确为主要成本，再实现内部增量更新；保留完整校验、CAS 与证据历史。
- 先改善全仓失效的解释，评估安全的影响范围；未识别依赖时继续保守核验，不能为少重跑而隐藏跨任务影响。
- 加入有价值的精简执行轨迹，支持接手和排错，不默认持久化并回灌整段聊天和全部提示词原文。

**退出条件：** 同场景对照证明有效成本下降，同时未降低任务定位、事实完整性、证据适用性、权限和报告一致性。没有收益证据的优化保留未实施，不为完成路线图扩大系统。

## 发布与兼容原则

- 每个阶段形成可独立审查的小批次；通过对应回归与真实插件路径验证后再升级，不把整张路线图作为一次大改动。
- 用户已有任务与报告保持可读，不自动移动目录、重命名任务、重绑项目或伪造当前证据。迁移需要显式设计和可恢复策略。
- 只有实际完成的项才改为完成；计划测试、沙箱反例和真实业务结果分别记录。
- 路线图不授予新的提交、发布、生产写入或对外沟通权限；按已有明确授权范围执行。

## 暂不做

- 不把每个会话变成一份独立需求，不强制为每个会话建立 worktree。
- 不增加第三个日常命令，也不让人维护会话 ID、JSON、报告阶段或分支表。
- 不把离线报告做成业务网站或远程审批后台。
- 不先建设完整调度平台、资源编排器或通用授权引擎；当前先解决已复现的定位、重复产出与快照竞争。
- 不预设 token 节省比例，不把固定模板在本地生成的 HTML 字节数当成模型输出 token。

## 已验证的后续收敛

0.22.0 根据 ZL-11 初始观察，先收敛已有状态/报告查询的材料加载与重复确认，未先建设通用增量更新。四个功能场景用于验证只读边界和完整流程分流；更多成本重复样本与跨环境归因仍待补。


0.23.0 先实现 ZL-13 的证据解释：保留原综合指纹，为新回执记录分项基线，短查询和按需报告展示原因及原关联范围；旧基线缺失保持未知。变更归属、依赖分析与安全减少重验范围尚未实现，ZL-13仍部分完成。ZL-09跨机器、ZL-11重复/归因、ZL-12及ZL-14状态不变。

## 下一阶段（2026-10-26 制定，基于 0.23.0）

R0～R3 的定位、按需报告和快照保护已基本落地，剩余问题主要不在功能缺失，而在两点：一是关键约束只靠提示词，评测里模型仍多次多余列目录、重复读取、触发 max_turns 或超时；二是全部真实模型评测都用 deepseek-v4.1-flash，尚无 Claude 模型数据。因此后续先补工程保障和评测口径，再按数据扩展功能。

| 阶段 | 目标 | 内容 | 退出条件 |
| --- | --- | --- | --- |
| M0 仓库卫生 | 本地、远端、安装版一致，回归可自动执行 | 同步到 0.23.0；增加 CI（unittest，macOS/Linux × Python 3.9/3.12）；选定 LICENSE（需仓库所有者决定） | CI 全绿；插件与 marketplace 严格校验通过 |
| M1 关键约束硬化 | 高风险规则不只依赖提示词 | 用插件 hooks 拦截：直接 Write/cp 改写 task.json/feature.json、status 路径内调用 update/render/begin、update 缺少 --expect-revision；CLI 返回明确 next_action，减少模型探索 | 每条拦截有回归测试；真实会话中被拦截时能按提示恢复 |
| M2 Claude 模型评测 | 结论适用于主力模型 | 用 Sonnet 5.5、Opus 5.5 复跑 quick-read、analyze、handoff、多会话、执行上下文场景，每场景 ≥3 次；记录 num_turns、超时/max_turns 率、冗余调用 | 形成按模型区分的基线，失败与冗余可量化 |
| M3 提示词瘦身 | 降低加载量和理解成本 | go-design.md/html 与 evaluations 移出插件运行时加载路径；entry-workflow 按分支拆分；长句与叠加限定改为短规则 | 首轮加载字节下降，M2 场景不退化 |
| M4 成本归因 | 判断 ZL-12 是否值得做 | 基于 M2 重复样本完成 ZL-11 归因 | 能回答全量 JSON 往返是否为主要成本 |
| M5 按证据扩展 | 只做有数据支持的功能 | ZL-12（取决于 M4）、ZL-13 变更归属、ZL-14 精简轨迹、ZL-09 跨机器关联 | 沿用 TODO 验收条件 |
| M6 真实使用 | 走出合成夹具 | 1～2 个真实项目试用并记录人的反馈；评估 Windows 写入锁（msvcrt） | 有真实用户反馈记录 |

顺序：M0 → M1 与 M2 并行 → M3 → M4 → M5；M6 可在 M1 后随时开始。暂不做的范围保持上一节不变。
