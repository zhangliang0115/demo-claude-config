1. 总体结构：三层协作，一份事实记录

插件由提示词编排层、Python 工具层、离线呈现层组成。Claude Code 提供模型、会话和工具执行环境；插件没有另外启动一个常驻调度服务。

  ↓ Claude Code 加载技能，带入参数

  ↓ 指示 Agent 读取

  ↓ Agent 结合用户范围、实际项目与现有任务选择分支

  ↓ Agent 使用宿主工具读代码、分析、编辑、执行实际检查

  ↓ 保存事实、核对版本与证据、派生当前行动

  ↓ 固定渲染器
report.html / feature.html / 按需 HANDOFF.md
  ↓ 人阅读、判断，必要时填写并复制反馈

必须区分两个路由：提示词中的事项路由决定 Agent 读什么、做什么；workflow.py 的条件分支决定记录目前说明什么、下一步提示谁做什么。后者不自动运行前者。

3. go 入口的完整契约

入口 frontmatter：name=go，user-invocable=true，disable-model-invocation=true。当前没有 context: fork、model 或 allowed-tools 配置；它未声明专用模型、独立执行上下文或技能级工具预授权。

用户输入通过 $ARGUMENTS 放入正文。${CLAUDE_PLUGIN_ROOT} 用于定位插件资料和脚本，不是业务项目路径。插件命名空间形成 /zl-dev:go。宿主层语义参考文末官方文档；本插件没有自行实现参数展开机制。

入口六项要求如下，完整原文在附录可展开：

  1. 定位业务项目；判断新任务还是同目标续作；不能因为只有一个历史任务就接入新需求。无参数或“继续”使用 continue 定位；多个候选由用户选标题。
  2. 探索、按需计划、实施和验证；先读项目约定与必要源码；用具体输入/操作/输出解释理解；关键未知集中提问，其余已授权工作继续。
  3. 多项目先调查和整体设计，再分配；共同规则变化先更新整体方案和子任务绑定，再运行 preflight。
  4. 只读本轮需要的内部动作；缺陷先复现；生产默认只读；生产写操作需要具体授权、范围、停止及恢复条件。
  5. 验证依据提前确定；优先支持的 unittest/JUnit 回执；独立审查或明确自审；失败先处理；区分检查、接受和行动授权。
  6. locate 获取记录版本 → 临时完整 JSON → update 比较后保存 → render。固定当前阶段模板，最终返回真实报告、验证结果和一条具体下一步；未保存不得称完成。

这些是 Agent 要遵循的指令，不是每项都存在工具层强制拦截。用户明确只分析、先设计或禁止修改时，本轮工作必须受该范围约束；通用“实现/验证”字样不应扩大授权。

8. 数据模型：谁写事实，谁算结论

task.json 是单项目任务事实来源；Agent 写业务语义，脚本检查结构并派生评估。不是每个字段都必填内容，也不要求人编辑 JSON。

字段组内容来源
id/title/project_path/kind任务身份、绑定项目、事项类型init/Agent，update 禁止改任务身份与项目绑定
why/summary/scope、behaviors/scenarios目标、范围、可观察行为和例子Agent根据用户与源码维护，模拟需标记
roles/assumptions/design/decisions职责、假设、方案与业务决定事实/推断/明确确认分开
implementation/changes/risks/rollback实际改动、变化、风险、恢复来自实际工作，不能以计划代替实现
evidence、runs/*行为关联、检查状态、命令、来源、版本、原始回执显式执行器或如实标注的模型记录
stage_details九个阶段各自 purpose/owner/summary/decision/exit_criteria/items固定字段，item.status 不等于批准
acceptance_setup、验收/发布 items环境/步骤/预期及实际观察/执行者/结果版本预期与观察分开，页面草稿不会直接写入
workflow_summary、provenance、stage_catalog当前行动、阻塞、可见内容、版本来源、模板目录读取/渲染时派生，不由Agent手填完成度

九个 focus_stage：requirements、solution、implementation、review、testing、acceptance、release、operations、handoff。与九种 kind 可组合，但并不保证每个组合都有完整独立设计。

三类版本：task_revision 是 JSON 精确字节哈希；current_fingerprint 是实际 Git 工作区与 semantic_contract 所选字段的指纹；assessment_revision 是不含生成时间等易变项的确定性评估哈希。反馈与快照同时核对三者，避免“代码没变就把旧业务判断当新批准”。

指纹排除展示摘要、观察、测试/审查结果等；包含项目绑定、范围、行为、场景、acceptance_setup、关键需求/方案字段和验收预期，非空发布核验契约也参与。以 semantic_contract 实际选择为准；它不覆盖外部系统和 Git 忽略文件，也不证明测试真实发生。

→ 成功：render；冲突：重读并合并，不覆盖

候选项目 → inspect识别清单/Git线索 → Agent读真实代码
→ feature.design整体方案 → contracts共同约定与版本

feature.json 的主要字段是 workspace_path、design(goal/flow/boundaries/decisions)、projects(path/task_path/responsibility/contract_version)、contracts、allocations(depends_on/owner)、integration(环境/版本/结果/证据)。项目数量不等于人数；sync不会分配人员或自动调度Agent。

整体方案变更必须先更新契约版本，再更新受影响子任务和验证。实际落盘是 feature update CAS → 更新受影响项目和子任务的契约基线 → preflight → 实施与 verify → sync → render。当前feature update不支持增删/重新绑定项目集合，不能承诺随意动态扩仓。

## 只读定位与安全更新

`/zl-dev:status` 只使用 `reviewable.py locate [任务目录] --project <真实项目>` 和 `status`。locate 返回标题、当前阶段、task_revision、指纹和已有报告路径；报告不存在时 report 为 null，不补建。它不会调用 continue/render/index，也不创建任务目录。continue 是推进入口，会重新渲染报告，不能用于只读查询。

修改记录时先运行 locate，读取完整 task.json，将合并后的完整 JSON 保存到系统临时目录，然后执行：

```sh
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/reviewable.py" update "<真实任务目录>" --project "<绑定项目绝对路径>" --from-file "<临时JSON路径>" --expect-revision "<locate返回的task_revision>"
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/reviewable.py" render "<真实任务目录>"
```

update 使用既有 schema 校验，只允许更新已有、绑定到指定项目的任务，不能改变 id 或 project_path；版本冲突时拒绝覆盖，必须重新读取并合并。可增加 `--expect-fingerprint "<locate返回的fingerprint>"` 检查当前代码及行为契约；它不同于 task_revision，证据和说明变化也会改变 task_revision。fingerprint 为 null 时不能声称已核对代码版本。update 本身不 render；更新失败不执行 render。

在 macOS/Linux 上，同目录临时文件和原子替换保护旧数据，协作 CLI 写入使用文件锁；外部编辑器不遵守锁，不能并发直接编辑 task.json。旧任务缺少绑定时需先人工核对，不能猜测补绑。CLI 不绕过系统权限或 agent 权限：项目外的 ~/.claude/zl-dev 产出访问可能需要对具体任务目录授权；非交互 Claude CLI 的 acceptEdits 不保证自动允许项目外读写或 Bash。拒绝时保留原记录，如实返回失败及待保存内容位置，等待该范围的权限解决，不建议全局 bypass。禁止改用 Write、cp、其他命令或工作区副本规避明确的权限拒绝，也不能声称未保存内容已落盘。

已有非空 revision 的证据必须保留原 id，不能改绑到新指纹；重跑后新增独立证据 id 并保留旧记录，也可清空 revision 显式标为未绑定。此检查防止误改已有记录，无法证明测试实际执行或防止恶意伪造新证据；不得通过改 id、删除旧记录或先清空再重绑来伪装重跑。

locate/status 返回 HANDOFF.md 的 handoff.path 与 freshness（current/stale/unknown/missing），同时核对精确任务版本和代码/行为指纹；发现过期、旧格式未知或缺失时，用 go 重新核对并按需显式导出，先保留手工补充，status 不自动修复或覆盖交接材料。

- change：规则前后对比、生效时间、历史数据与在途任务。
- bugfix：复现、根因、修复机制、回归证据。
- refactor：结构变化及必须保持的行为。
- performance：同条件基线、结果、代价和正确性。

在实现变更后，重新执行受影响验证；保留旧证据但标记过期。绑定证据的代码状态应覆盖相关工作区内容，不能只用 HEAD 代表未提交改动。仅报告脚本真实支持的版本检测能力；无法确定时手工标记待验证。

每条关键用户路径记录前置条件、操作、预期结果、实际结果、环境、执行时间、工具、原始日志或截图位置；区分 simulation 与 recorded。不能把 HTTP 200 当作业务正确，也不能把模拟 API 测试当作完整真实链路。涉及真实支付、消息、第三方服务时使用已授权测试环境，不自行触发真实交易。无法运行时记录 blocked 和需要的条件。人工核验作为独立记录，不由 AI 自动补签；受托 AI 验收另记实际判断者、标准、范围与授权来源。

# 人与 AI 的协作模型

本页定义产品责任与判断原则，不表示所有规则已由脚本实现。本轮运行时先支持条目级受托验收、来源与版本区分，以及完成后不重复要求人工核验；通用行动授权、按动作划分阻塞和偏差豁免仍是后续设计边界，不是已实现能力。

## 插件定位

帮助人把目标交给 AI，在变化和交接中持续保持共同理解，并在需要人判断时提供足够清楚的材料。插件同时约束 AI 如何推进工作、如何留下可核对事实，以及如何把问题交回人。

HTML 是面向人的阶段协作报告：呈现目标、差异、当前结论、依据和待决事项。它既不替代业务系统，也不要求读者遍历技术流水账。局部展开、比较、填写并复制反馈服务于理解和沟通；业务接口、生产操作和数据维护不由报告执行。

## 先区分三类事实

1. **执行与验证**：谁实际做了什么、在什么环境运行、观察到什么、哪些未验证。可以由 AI 承担，也可以委托他人；来源与版本必须如实保留。
2. **结果接受**：结果是否满足约定目标，哪些剩余偏差可接受。可按清楚的标准委托 AI 代验，也可能需要人的偏好、体验或业务判断；不能从点击复制、测试通过或模型自述推断接受。
3. **行动授权**：接下来允许执行哪些动作、对象和范围。既有明确授权继续有效，委托范围不能由 AI 扩大；验证通过不自动生成新的生产变更、发布或对外沟通权限。

执行者、接受者与授权者可能相同，但三类事实不能合并为一个“通过”标记。人承担责任不意味着每个步骤都必须重复亲手执行；AI 承担执行也不意味着可以代写人的身份或未经授权作出承诺。

### 检查委托与结果接受委托

“帮我跑验收测试”委托的是检查：AI 记录执行与结论，不据此推断用户接受交付。“按这些标准替我验收，满足后按已有授权继续”还委托了标准内的结果判断：AI 可以记录受托验收结论，并继续已有授权内的工作。后者的执行者和判断者仍是 AI，不能登记为人工签字。

两类委托都应保留原话或可核对来源、适用目标与范围，以及结果所对应的版本。接手时复用已有明确委托；只有范围、标准或条件发生实质变化才澄清缺失部分。无需把这一区分变成两道新审批，也不能从含糊的“继续”扩出新的验收或发布权限。

### 失败、偏差与阻塞

失败、受阻和未执行是证据事实，不因为结果被接受就改写成通过；但它们也不自动意味着整项任务停止。应说明缺口影响哪个目标、阻止哪一步，以及哪些独立且已授权的工作仍可推进。

可豁免的偏差只有在明确接受了具体影响与范围后，才可作为带偏差接受的结果；保留原失败事实、接受依据和剩余风险。委托 AI 按原标准验收，不自动授权 AI 降低标准或接受标准外偏差。不可豁免的约束应注明依据，不能只用“高风险”代替约束来源。对其影响范围以外的工作不制造全局阻塞。

## 人和 AI 分别承担什么

| 协作问题 | AI 的责任 | 人保留的判断 |
| --- | --- | --- |
| 目标模糊 | 查实际现状，把描述转为具体例子，列出假设与推荐，解释不同选择的影响 | 目标是否值得做，关键业务取舍是否符合实际 |
| 方案与实现 | 在授权范围内决定常规技术细节，小切片实现，检查与修复，不把可逆细节反复退给人 | 影响目标、成本、风险承受或组织规则的选择；未知约束的补充 |
| 审查与验证 | 先完成可工具化验证，主动找反例，说明证据能支持什么；失败先查明修复 | 无法由现有证据代替的体验、业务或风险判断 |
| 明确委托代验 | 在委托范围与标准内实际执行，记录 AI 来源、结果与未覆盖项 | 委托范围及其变更；没有被委托的决定 |
| 换人或换工具 | 交出当前目标、实质变化、版本差异、未决问题和可执行第一步，接手时核对事实 | 责任归属、理解差异和真正影响目标的分歧 |
| 发布与生产运维 | 在已授权的具体范围执行并验证，保留影响、停止条件和恢复依据 | 新增高影响范围或无法从授权推出的决定；不重复索取已经明确的同范围授权 |

“需要人判断”不能被用作 AI 跳过调查、测试和修复的出口。交回的问题应包含事实、可选方案、推荐理由和选择的后果，而非笼统要求“请全面检查”。

## 什么时候打断人

只有缺少会影响正确推进的目标、业务决定、权限或外部条件时才集中提问。其余已授权且能验证的工作持续推进。不同项目数量、阶段数量和人员数量不能自动产生相同数量的批准关卡。

阶段完成不等于自动进入发布；也不等于必须找人补一个签字。一次明确的委托要在后续状态和报告中持续生效，不让用户重复表达。

## 报告应从协作问题推导

每份报告先回答：在解决什么问题、本阶段实际结论、本轮实质变化、结论依据和下一步由谁做。没有待人决定的事项时，明确说明当前无需人处理；不为填满固定位置而虚构一个问题、操作表单或审批。

按本阶段的协作任务组织主内容：

- 理解需求：具体目标、边界、例子和关键未决假设。
- 选择方案：推荐、替代、影响及真正需要选择的事项。
- 推进开发：实际变化、偏差、当前阻塞和 AI 下一步。
- 审查验证：成立的发现、影响、复核结果、剩余缺口和证据来源。
- 完成交付或代验：对照约定的结果、由谁验证或接受、委托范围与剩余事项。
- 交接：相较接手基线改变了什么、还缺什么、从哪里继续。

# 跨项目功能：整体设计，分项目实施

## 核心顺序

识别候选项目 → 检查现有职责和调用关系 → 设计整个功能 → 确定项目边界与共同契约 → 拆开发任务及依赖 → 分项目实现 → 整体联调与人工核验。

一个功能一个 feature.json 和阶段报告 feature.html，各项目各自一个 task.json/report.html。页面根据 phase 默认打开当前阶段（discovery/design/contracts/implementation/integration，也识别 solution/testing/acceptance 等常用别名），页首读取 design.goal。导航用于查看同一功能的已有材料，不代表每次必须重走所有阶段。各阶段可填写判断和备注并复制给 AI；复制内容含功能编号、契约版本、报告生成时间和阶段，只是草稿，不自动批准方案或写回记录。设计负责人和实施者可一人兼任，也可多人协作；项目数量不等于人员数量。换人或换 agent 要复述理解，同一个人不必人为交接给自己。

## 第一步：识别，不预分配

用户给出工作区或候选项目路径。仅在提供范围检查，不扫描个人目录或读取无关项目。脚本 inspect 识别清单文件及 Git 版本等事实，AI 另行读取项目约定、入口、接口、业务实现和现有测试，记录带源码位置的观察。不能因为名叫 admin 就认定所有管理业务都应在那里，也不能因为目录叫 api 就假设它掌握业务数据。

检查不可访问的项目时，标记未知并请求必要路径或访问方式；不可把猜测当已分析。远程只拿到方案、没拿到代码时，写清识别限制。

## 第二步：整体方案先于项目任务

feature.design 记录 goal（整个目标）、flow（完整用户和数据路径）、boundaries（按证据提出的职责边界）、decisions（取舍和待决问题）。必须从完整功能角度设计主路径、异常状态、权限、幂等、历史数据、兼容性和验收。

contracts 列出跨项目共同约定及版本。每条 {id, version, description, status: proposed/confirmed}。全局 contract_version 是整体方案基线，例如 v1；仅人明确确认关键规则后，才能记录对应确认。确认目标不是要求用户批准每项内部实现细节。

## 第三步：再分项目开发

allocations 中每条 {id, project_id, summary, depends_on: [], contract_version, status, owner}。owner 可同一个人也可不同人，未知留空。depends_on 引用其他 allocation.id，禁止环。业务代码实施前运行 `feature.py preflight /功能目录`。它只读检查当前整体方案基线、所有共享契约确认、项目/子任务版本和切片依赖版本；有缺口返回退出码 2，先解决问题再开始实施。它不是 Edit hook，不能技术上阻止绕过指引的任意编辑，也不会因为通过就证明依赖已实现。先实现真实依赖；契约已明确时可以采用清楚标记的 mock 并行，但 mock 通过不代表联调通过。

projects 每条 {id, path, responsibility, task_path, contract_version, status, owner}。task_path 指向明确的子任务绝对目录（默认在用户 .claude 下），path 为本机仓库路径。外置子任务的 project_path 必须与此项目真实路径一致；不能借用其他项目的证据。为其他机器交接时应重新绑定本机路径，不照搬别人的绝对路径。

子任务额外记录 feature: {id, path, contract_version}，保持子任务的需求与总方案关联。feature.py sync 只读取显式关联任务并汇总，不替任何项目修改代码，不自动创建团队或派发给他人。`projects[].snapshot` 是派生快照，只能由 sync 更新；AI 不得手改其中计数、问题或新鲜度来使状态变绿。历史失败和过期证据仍计数、保留追溯；当前版本有全部行为覆盖且无当前未通过记录时，历史失败不再永久阻塞。当前失败/阻塞/未执行不能被另一条 passed 简单抵消，未知或未覆盖仍阻塞。

## 第四步：变更与整体验收

影响共同规则的改动先更新整体方案版本，再列出受影响项目。每个项目按新基线实施、验证并更新 contract_version。报告展示版本不一致和快照过期，不能悄悄覆盖旧版本。不同 AI 工具读取同一总方案和子任务结构；不要只靠聊天上下文。

integration 条目 {id, scenario, environment, status, versions: {project_id: deployed_revision}, evidence}。记录整条用户路径、真实部署版本、环境、结果和原始证据。模拟/未执行要明确标记。脚本的汇总与新鲜度检查不等于发布批准，也不能自动证明线上或 E2E 通过。

## CLI 和持久化

```sh
python3 /插件路径/scripts/feature.py init order-cancel --workspace /工作区 --title "订单取消" --project admin=/工作区/admin --project api=/工作区/api
python3 /插件路径/scripts/feature.py locate /功能目录
python3 /插件路径/scripts/feature.py update /功能目录 --workspace /工作区 --from-file /临时目录/feature-next.json --expect-revision <locate返回的feature_revision>
python3 /插件路径/scripts/feature.py inspect /功能目录
python3 /插件路径/scripts/feature.py preflight /功能目录
python3 /插件路径/scripts/feature.py sync /功能目录
python3 /插件路径/scripts/feature.py render /功能目录
python3 /插件路径/scripts/feature.py status /功能目录
```

更新方案时，先 `locate` 获取精确 feature.json 字节的 `feature_revision`，读取当前 feature.json，以完整对象在可写临时目录准备 `feature-next.json`，再用上述 `update` 导入。源文件权限失败会如实报错；不要通过直接 Write 用户目录绕过环境的写入限制。`update` 校验 JSON、固定功能 id/工作区/项目 id 与路径集合，并拒绝改写派生快照；本命令暂不支持增删或重新绑定项目。`--workspace` 必须匹配初始化记录的工作区。版本冲突时重新 locate、重读合并，不能强行覆盖。更新只保存数据，不生成页面、不确认业务规则；随后按需要 preflight、sync、render。

子任务快照绑定规范化的 task_path 和 task_id；即使代码与行为指纹相同，切换任务后也必须重新 sync。旧快照缺少绑定时按过期待核对处理。

`update`、`inspect` 和 `sync` 共用协作锁并原子替换文件，inspect/sync 还检查读取以来的版本变化。外部编辑器不遵守该锁，不要同时直接编辑 feature.json；这些保护也不提供超越系统权限的写入能力。当前写锁依赖 fcntl，Windows 等缺少它的平台仍可运行 locate/status/preflight 等只读命令，但写入命令会明确报不支持，不进行写入。

总任务默认保存在 `~/.claude/zl-dev/projects/<工作区名>-<路径哈希>/features/<slug>/`。用 `--workspace <共同工作区绝对路径>` 固定归属；各项目子任务仍按各自项目区分。inspect 写观察，sync 写快照，render 生成 feature.html；这不是后台监听。未同步、不可访问和版本变化都应保留为缺口。不要仅传总目录给原来的 task CLI，它使用另一份 task.json 数据格式。

# task.json v1 数据约定

Python 3.9+，UTF-8 JSON 对象。以 scripts/reviewable.py 的 validate 为基础结构校验，以下语义仍需人工与 AI 核对。

必填：version=1；id/title 非空字符串；kind 为 feature/change/bugfix/refactor/performance/migration/upgrade/incident/operations。
summary/why/scope/stage/rollback 为字符串。changes/risks/acceptance 为字符串数组。

对象数组字段（无内容用 []）：
- behaviors: id（唯一）、before、after、status。明确规则已确认/已实现是不同事实；验证状态由 evidence 单独呈现。
- scenarios: title、kind（simulation/recorded）、steps（action/result 对象数组）。recorded 只能来自真实记录。
- implementation: title、description、files（路径或路径数组）。
- decisions: id、question、recommendation、status（pending/confirmed）、owner、source、at。confirmed 需人的明确依据。
- evidence: id、behavior_ids（必须引用存在行为）、status（passed/failed/blocked/not_run）、command、summary、revision、source、executed_at；可加 actor/environment。source 是原始记录位置，页面不自动执行或读取路径。
- roles: role、owner、responsibility、accepts。
- assumptions: id、statement、basis、status（pending/confirmed/refuted）、owner、check。
- design: id、title、description、alternatives、tradeoffs、status。
- handoffs: id、from、to、deliverable、readback、open_questions、status（pending/accepted/rejected）、actor、at。
- timeline: at、actor、action、reason、impact。
- operations: id、type、environment、impact、observation、hypothesis、action、authorization、stop_condition、rollback、result、verification、status、owner。

## 证据新鲜度
fingerprint 绑定 Git 工作区内容与行为约定（含场景、验收、假设、方案、交接及操作计划）。没有 Git 时 UNKNOWN，不能声称当前有效。验证前后计算指纹，完全相同才绑定 evidence.revision；指纹变化必须重新验证，不能只刷新指纹。指纹匹配不证明命令实际运行。

HTML 生成可读的反馈文本，填写后点“复制给 AI”并粘贴到会话，不直接改 task.json，不代表审批或接收。人把草稿交回会话后核对任务与版本，再记录明确授权。跨工具接手包不包含凭据，不自动执行任何命令。

## 用户级项目存储（0.5.0）

新任务的 `project_path` 保存原项目真实绝对路径。产出目录在用户 `~/.claude/zl-dev/projects/<项目名>-<路径哈希>/tasks/<slug>/`；代码指纹读取 project_path 的源码，不能对 `.claude` 目录计算代码指纹。项目不存在时返回未知，不回退到其他仓库。旧任务缺少绑定时仍按原任务所在 Git 仓库定位。

```sh
python3 scripts/reviewable.py init cancel-order --project /workspace/orders --title "取消订单" --kind feature
python3 scripts/reviewable.py render cancel-order --project /workspace/orders
python3 scripts/reviewable.py status cancel-order --project /workspace/orders
```

位置参数是简单 slug 时按用户目录解析，`--project` 省略时使用当前目录；传入绝对路径或含路径分隔符的路径则继续支持原显式目录。日常插件必须使用默认用户目录，仅在用户明确指定旧目录或测试示例时使用显式路径。slug 不得为 . 或 ..。

`reviewable.py index --project /项目绝对路径` 会生成该项目 tasks/index.html。跨项目 CLI 的 JSON 响应带 output_dir，供后续定位；render 则直接返回 feature.html 的绝对路径。不要用 shell 引号包裹 `~` 来期望 shell 展开；优先使用 slug + --project/--workspace 或脚本返回的绝对路径。

## 0.6.0 路由与证据
continue [任务目录或 slug] --project /项目路径：省略任务时仅在恰好一个任务的情况下恢复；0 或多个返回候选清单。不会执行开发命令。返回 next_action 与 step（understand/decide/implement/verify/accept），供 AI 继续；accept 表示待人工核验，不是已验收。

workflow_summary 是渲染时计算结果，不让 AI 填写完成度。指纹仅使用 semantic_contract 明确选择的行为字段；阶段 testing/review 的结果、handoffs、人员和展示摘要不参与。阶段 requirements/solution 的核心内容及 acceptance 预期仍参与。旧证据需重新验证。

时间展示统一为 `yyyy-MM-dd HH:mm:ss`，时区 Asia/Shanghai（UTC+8）。原始数据保留带时区的 ISO 时间，页面与复制反馈格式化显示，不改变证据记录本身。

## 显式执行与可重新核算的测试回执

内部 CLI（不是新增斜杠命令）：

只执行调用者显式提供的 argv，以绑定项目为 cwd、shell=False；不会从 task.json、HTML 或 prepare_command 读取并运行命令。调用者仍须检查实际测试的环境和外部连接。JUnit 结果必须为本轮新文件；建议放在源码外或 Git 忽略的测试输出目录，避免结果文件本身改变源码指纹。执行不保证测试真正覆盖所引用行为。

每次运行在任务 `runs/verify-<唯一ID>/` 保留 stdout.log、stderr.log、receipt.json；JUnit 额外保存 result.xml。超时结束本次进程组并保留记录。回执记录 argv/cwd、开始结束时间、进程退出码、运行前后任务 revision 与代码/行为指纹、task 身份、行为引用、日志 SHA256 和解析统计。只在指纹和任务 revision 稳定时，以 CAS 追加独立 evidence，不修改已有证据，不渲染 HTML；冲突时只保留回执。返回 0 必须已追加证据、非零测试实际通过、没有跳过且版本稳定。

支持 unittest 的唯一 Ran N + OK/FAILED 摘要及 JUnit 的实际 testcase；0 项、跳过项、未知格式、缺摘要、非零退出、超时均不能成为 passed。单个输入文件只解析前述 16 MiB 上限以内的完整内容，超出则不解析，不记通过；这个限制不限制子进程写盘量，执行期间的原始 stdout/stderr 可能很大。部分 skip 也采用保守策略，不记 passed；如需单独证明未跳过的相关行为，应显式选择并重跑独立检查，不能隐藏跳过项。输出中的测试名或日志可以被程序伪造；**日志解析不等价业务覆盖或身份认证，不抵抗有本地写权限者同时伪造日志与回执**。

新增 evidence 可引用 `verification_receipt: {path: "runs/verify-.../receipt.json", sha256: "..."}`。报告/status 的 assessed 会重新检查回执哈希、任务与行为身份、原始日志哈希并重新解析；派生 `verification_source` 为 `parsed_result`、`claim`（旧记录/仅模型声明）或 `invalid`。合法解析派生 `parsed_result={format,counts:{total,passed,failed,errors,skipped},status}`；模型手填这两项会被覆盖。无效回执保留 `claimed_status`，有效 status 降为 not_run，不能使任务就绪。读取不会执行测试或改写文件。

`acceptance_setup` 可选对象，只允许字符串字段 `environment/prepare_command/entry_url/baseline/stop/notes`。entry_url 仅 http/https 或空；命令只展示，绝不自动执行。这些前置约定参与行为指纹，改变后旧证据过期。

acceptance、release 阶段条目可选 `reviewed_revision`（字符串）、`reviewer_kind`（human/ai/unknown，旧记录默认 unknown）、`verification_mode`（manual/assisted/automated，旧记录默认 manual）。执行者与核验方式不能由页面替人认证。核验版本、执行者、actual/result 等反馈元数据不参与行为指纹；已定义的场景、操作与预期仍参与。

## 页面快照与明确人工结果

acceptance/release 条目可选 result_status: pass/fail/blocked/not_checked，作为明确结果，与展示文本 result 分开；不参与行为指纹。只有有当前指纹、reviewed_revision 匹配、reviewer_kind=human 的显式结果参与本版人工判断。自由文本与 status=done 不自动转译；AI 角色记录不会成为人工签字。核验接受不等于发布批准。

# 阶段专用展示协议

必须使用 templates/stages.json 定义字段，以及 assets/stages.js 与 stages.css 的固定渲染。AI 只填写 task.json.stage_details；不得为任务另写 HTML、CSS、脚本或自定义字段。所有页面随 report.html 离线内嵌，不依赖 CDN。

## 每个阶段的共同结构

items 必须有阶段内唯一 id 和 status：pending/in_progress/blocked/done。done 仅表示记录者声明条目处理完成，不等于人已批准或验证已通过。其余展示字段均为字符串；未知字段拒绝，避免不同 AI 发明不同格式。

## 固定阶段与字段

### requirements — 需求理解
核对原始描述与解释，明确边界和验收例子。

original：原始描述 | interpretation：理解结果 | boundary：范围与非目标 | example：验收例子

### solution — 方案设计

name：方案名称 | approach：如何工作 | benefit：收益 | cost：成本与代价 | risk：风险 | flow：交互或架构流程

对照交出内容与接收者复述，暴露理解差异。

deliverable：交出范围与版本 | receiver：接收人 | readback：接收者理解 | gap：差异与疑问 | next_action：第一步

### implementation — 实施过程
对照计划与实际，解释变更和影响。

planned：计划切片 | actual：实际实现 | deviation：偏差与原因 | impact：影响范围 | source：代码位置

### review — 代码审查
按严重程度查看发现、修复和复查证据。

severity：严重程度 | finding：发现与成立条件 | source：代码位置 | fix：修复说明 | recheck：复查结果

### testing — 自动测试与 E2E
逐步查看预期、实际与证据；模拟不代表执行。

case：测试场景 | mode：simulation / recorded | environment：环境与前置条件 | expected：预期结果 | actual：实际结果 | source：日志或截图位置

### acceptance — 人工验收
人亲自核验关键场景；页面选择只生成草稿。

scenario：验收场景 | instruction：操作步骤 | expected：预期 | actual：人工实际观察 | reviewer：核验人 | result：接受 / 退回 / 未核验

### release — 发布与回滚
核对放行条件、观察指标、停止条件及恢复办法。

check：发布检查项 | environment：目标环境 | authorization：授权记录 | metric：观察指标及阈值 | stop：停止条件 | rollback：回退步骤 | actual：执行结果

### operations — 运维与复盘
沿事件时间线区分事实、假设、动作与恢复证据。

at：时间 | observation：事实与影响 | hypothesis：诊断假设 | action：动作及授权 | verification：恢复指标 / 用户路径 | followup：防复发行动及负责人

## 特殊字段与交互

- solution 展示结构化方案比较和流程说明，不声称自动生成了可运行产品原型。
- acceptance 的页面选择与备注只生成可复制反馈，并绑定 task_id、版本及阶段，不直接改变已确认记录。人明确回传后再核对版本并更新。
