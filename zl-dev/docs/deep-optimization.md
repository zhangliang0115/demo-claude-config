# 0.13：减少误判与人工阅读负担

本轮审查聚焦同一条日常流程：模糊需求、整体设计、换人或换工具实施、AI 验证、负责人核验。用户仍只使用 `/zl-dev:go` 和 `/zl-dev:status`。

## 本轮选择

| 已复现的问题 | 改进 |
| --- | --- |
| 有通过记录、同时存在未解决 P0/P1 问题，仍建议人验收 | 状态脚本统一计算当前阻塞和行动；高风险问题必须有当前、无矛盾的复查依据 |
| 页面一边要求 AI 修复，一边把布局问题当作人当前必须完成的动作 | 首屏消费同一份 `primary_action`；其他待决保留，技术阻塞先处理 |
| 模型填写的“通过”与真实日志统计外观一样 | 内部 verify 执行显式测试命令，解析结果、保留日志和回执；页面区分模型记录、已解析结果与无效回执 |
| 人不知道怎样启动核验，历史观察在重新打开后消失 | 准备区说明环境、入口、前提和停止方法；已记录结果只读显示，新草稿独立保持未填写 |
| 同一验收要求在两套字段中分叉 | 有结构化验收项时优先使用，旧字符串仅兼容；不再新增另一套人工维护的概览字段 |

## 状态如何决定

当前失败、阻塞或未执行证据优先进入 AI 核查；P0/P1 未解决或缺少当前复查依据时进入 AI 审查。两者不能被显式 `focus_stage=acceptance`、其他通过记录或布局待决掩盖。跨项目总览消费相同的技术阻塞结果。

没有上述技术阻塞后，才依次判断目标是否明确、业务规则是否待决、是否有实际实施和行为证据，以及人应核验的具体事项。既有模型声明仍可读取，但明确显示来源；声明的数量不构成真实执行或业务覆盖证明。

## 测试记录如何产生

AI 可在已有内部 CLI 中使用 verify；人不用记住这个命令。先固定环境准备和验收预期，再执行测试。执行器检查任务绑定，使用显式 argv、`shell=False` 和绑定项目目录运行，记录前后版本、退出码、日志摘要及 SHA256。它通过 CAS 新增记录，不改绑旧证据，也不自动重新生成页面。

首批支持 Python unittest 与 JUnit。退出 0 但没有可解析执行摘要、零项、包含跳过、超时或版本变化，均不当作完整通过。JUnit 校验每一层汇总与实际 testcase；畸形或被修改的回执不能继续标为可信解析。自定义浏览器 JSON 尚未接入，旧记录继续标明为模型记录。

读取时还会核对回执身份与哈希、原始日志哈希，并重新解析。任何有权限者仍可联合伪造本地文件；该机制防止误记与意外篡改，不提供执行身份认证，也不证明测试覆盖了所关联行为。16 MiB 是解析上限，不是子进程磁盘输出配额。

## 人怎样核验

人工阶段先看“开始核验”：环境、入口、准备命令、基线和停止方法。命令只能复制，HTML 不执行它；缺少准备资料时明确显示缺口。辅助故障注入标为需要 AI 协助，不能伪装成普通点击步骤。

每项核验显示已有观察、结果、记录者和版本；旧版本或没有版本的记录不会默认继承。AI 测试角色与来源未知均明确标注，`reviewer_kind=human` 也只是记录来源标签，不是签字认证。填写新反馈不会覆盖旧结果，复制只带本次填写内容，未填项保持未知。
