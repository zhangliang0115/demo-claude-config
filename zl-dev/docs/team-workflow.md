# 多人、多工具协作协议

## 目标与边界
需求不明确时允许提出自洽方案，但“自洽”不等于“业务正确”。先记录事实、假设、待决问题和可操作例子。不同工具与模型共用 task.json、HTML 和 HANDOFF.md；统一材料结构不能保证模型能力一致，必须靠可复现证据和适用的结果判断收敛。

协作原则见[人与 AI 的协作模型](collaboration-model.md)。脚本支持条目级受托验收及来源区分；通用行动授权、按动作判断阻塞和偏差豁免尚未完整支持，不得仅靠改写报告文案声称已实现。

## 人的职责与按需固定页面

| 阶段 | 负责人职责 | AI 职责 | 固定页面 | 交出条件 |
|---|---|---|---|---|
| 需求理解 | 提出目标、业务痛点、成功标准 | 查现状、提出假设与方案选项 | 一分钟概览、业务变化、场景演示 | 关键未知有负责人；高风险规则有人确认 |
| 方案设计 | 决定取舍、范围、预算及约束 | 给场景、原型说明、边界、方案比较 | 方案与职责、场景演示 | 主路径、异常路径、非目标、验收样例可理解 |
| 下发交接 | 方案负责人说明当前版本与未决问题 | 输出跨工具接手包 | 跨人交接 | 接收人复述目标、边界、第一步及疑问 |
| 边做边澄清 | 实施者暴露矛盾，负责人决定需求变化 | 小切片实施，记录偏差和新增假设 | 实现解释、业务变化、变更记录 | 不静默把实现便利改成业务规则 |
| 独立审查 | 审查者关注业务不变量及高风险点 | 从约定独立找反例 | 验证证据、需要你决定 | 问题已修复或责任人明确接受剩余风险 |
| 验收 | 明确接受标准；自行判断或明确委托标准内的接受判断 | 执行 E2E、异常和回归检查；有明确委托时按标准判断接受 | 场景演示、验证证据、核验结论与缺口 | 区分检查结论与接受结论，保留实际判断者与委托来源，缺口不抹平 |
| 发布运维 | 操作负责人批准范围并判断恢复 | 只读诊断、操作建议、恢复验证 | 生产与运维 | 授权、停止条件、恢复方法和实际结果齐备 |

角色可兼任，阶段划分不自动产生审批关卡。每项确需人决定的事项有 owner；AI 不得冒充人的身份或补写人工签字。明确委托按标准接受结果时，AI 可在委托范围内作判断，记录实际 AI 来源及委托依据，不登记为人工批准；仅委托跑检查不等于委托接受结果。接手状态用 pending/accepted/rejected，只有接收方明确确认才写 accepted；接收方为 AI 时也如实标记其身份与接手范围。记录 actor 和 at；不知道工具或模型时写 unknown，不猜。

## 渐进澄清
允许先实现可逆且授权明确的小切片。每次发现新规则：记录 observation → assumption → decision → 更新行为约定 → 重新验证受影响场景。金额、权限、数据删除、生产操作、外部接口兼容性不能由执行者 AI 静默决定。已获得的具体授权继续有效，不重复请求。

## 端到端验证
每条关键用户路径记录前置条件、操作、预期结果、实际结果、环境、执行时间、工具、原始日志或截图位置；区分 simulation 与 recorded。不能把 HTTP 200 当作业务正确，也不能把模拟 API 测试当作完整真实链路。涉及真实支付、消息、第三方服务时使用已授权测试环境，不自行触发真实交易。无法运行时记录 blocked 和需要的条件。人工核验作为独立记录，不由 AI 自动补签；受托 AI 验收另记实际判断者、标准、范围与授权来源。

失败和未执行的事实应保留，并说明受影响目标与受阻动作；独立且已授权的工作继续推进。可豁免偏差需要明确接受其具体影响，原检查结果仍保持失败或未执行；原标准内的验收委托不自动允许降低标准。不可豁免约束说明依据。验收完成不自动产生发布权限，也不要求对已有同范围授权重复批准。

## 生产事件 incident
先确定用户影响、发生时间、环境、事件负责人和已知事实。只读收集日志/指标（脱敏），列出可证伪的假设。先止损还是继续诊断由影响和已有授权决定。每个写操作记录精确对象、动作、授权来源、观察指标、停止条件和回退办法。高影响操作执行前须有明确授权；已授权的范围不重复询问。恢复必须用用户路径或关键指标验证，不因进程重启成功就宣布恢复。之后补时间线、根因证据、修复和防复发任务。

## 日常运维 operations
巡检、配置变更、发布检查、容量检查均可用同一操作卡。检查和建议不等于已执行；已执行不等于验证通过。页面永远不执行 shell 或生产 API。

## 标准模板规则
需要 HTML 时必须使用随插件提供的固定模板和 schema，不能每次另写网页。关键事实及时更新同一个 task.json，报告按 entry-workflow.md 的产出策略独立生成；不每阶段 render，不批量 index 其他任务。未到阶段显示未记录；不要为填满模板编造内容。场景、规则和证据通过稳定 ID 关联。HTML 的反馈只是一份草稿，需人明确发回会话，核对任务版本后再记录；不自动合入审批。

## 跨工具交接
运行 handoff 生成 HANDOFF.md，连同任务 JSON、已有报告的时效说明和必要设计/证据通过团队既有渠道交接。Codex、Cursor 等读取该文件并执行 Python CLI，不假设支持 Claude 命令。接收者先独立阅读真实代码并复述，再继续。交接包不是远程同步系统，不自动推送给他人。

交接包只替换生成标记之间的内容，人工笔记放在标记之外。旧格式迁移会保存唯一备份，新包指向旧材料；不要把旧材料中的状态当当前结论。接手先核对当前行动、report_state 和 task_revision/assessment_revision，HTML 过期时先读当前数据。人工退回使用明确 result_status 并保留原话与对应行为版本；不能将 AI 观察登记为人确认。

## 多会话的焦点与职责

长期任务允许跨会话延续，同一目标也可由不同会话分工。按[会话关联](session-context.md)使用工具命名空间、可靠会话 ID 和项目作用范围保存各自焦点；它不代替 roles/handoffs 或执行授权。主会话核对目标后控制 bind/clear；子代理仅使用分配的明确目标，不改父会话关联。接手须核对真实代码、环境和资料，不能从另一会话的索引继承权限。不同 task 目录不保证共享源码、端口和测试数据隔离。

## 只读分析职责

用户确定要解释的问题与可读范围，AI 沿实际源码追踪并给可核对依据，继续查可访问断点；确实缺材料时只问具体缺失，范围外保持未知。此类任务使用 kind=analysis，不要求实施、运行测试、人工验收或补签。跨仓源码范围不等于批准业务变更，详见 [analysis-workflow.md](analysis-workflow.md)。
