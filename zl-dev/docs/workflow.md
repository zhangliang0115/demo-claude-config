# ZL Dev 工作协议

HTML 是首要交付，`task.json` 是事实来源。页面不能代替代码、测试或人的判断。默认中文交流和页面内容，跟随用户明确语言偏好。

## 项目和任务

1. 读取项目自己的 CLAUDE.md、AGENTS.md 和相关开发说明。先查现状，不臆造构建命令、框架或目录。
2. 任务目录默认为当前项目 `.zl-dev/tasks/<slug>/`，slug 用简短英文字母、数字、连字符。传入已有目录时继续原任务；多个候选且无法判定时请用户指定，不覆盖别的任务。
3. 工具仅依赖 Python 3.9+ 标准库：
   ```sh
   python3 "${CLAUDE_PLUGIN_ROOT}/scripts/reviewable.py" init ".zl-dev/tasks/<slug>" --title "任务名称" --kind feature
   python3 "${CLAUDE_PLUGIN_ROOT}/scripts/reviewable.py" render ".zl-dev/tasks/<slug>"
   python3 "${CLAUDE_PLUGIN_ROOT}/scripts/reviewable.py" status ".zl-dev/tasks/<slug>"
   ```
   这是模板：替换占位符，用独立参数和正确 shell 引号，不把用户描述拼接成可执行脚本。
4. 先阅读 init 生成的 task.json，保持字段类型和结构，按实际数据编辑。不要创造与渲染器不兼容的新格式；参照插件示例和 `docs/schema-reference.md`。一次阶段结束后渲染，返回 report.html 绝对路径。
5. 任务类型：feature 新功能、change 规则调整、bugfix 缺陷、refactor 重构、performance 性能、migration 数据迁移、upgrade 技术升级。

## 理解优先

页面按“为什么做 → 可观察变化 → 业务规则 → 实现解释 → 待决事项 → 验证证据”组织。先给人具体输入、操作和预期输出，不从文件清单开始。未实现的场景标为设计模拟；只有实际执行过的记录才叫测试记录。默认页面不连接运行中的业务系统。

- feature：用户路径、异常路径、权限边界。
- change：规则前后对比、生效时间、历史数据与在途任务。
- bugfix：复现、根因、修复机制、回归证据。
- refactor：结构变化及必须保持的行为。
- performance：同条件基线、结果、代价和正确性。
- migration：转换规则、预演、核对、失败恢复；回滚代码不等于恢复数据。
- upgrade：兼容性、新旧行为、工具链；可使用已有现代化工具产物但不假装自动集成。

## 决策、范围与实施

区分人确认的规则、源码观察和推断。AI 不得默认决定金额、权限、不可逆修改等关键业务问题；列出选项、推荐理由和影响，集中询问。已授权且明确的事项直接做，不反复确认。低风险小改动简化流程；不要强制生成大量文档。

用稳定 ID 表达行为约定和场景，关联实现与证据。状态不能混用：规则已确认 ≠ 已实现 ≠ 已验证。只实现可独立解释和验证的小切片，不混入无关重构。显式记录范围外事项和实现偏差。

## 审查与验证

有独立代理能力时使用插件 reviewer 做独立审查，给它用户确认规则、差异、相关上下文，而非仅给实现者总结。没有该能力则进行单独审查轮次，并明确“同一代理自审”，不得声称独立审查。审查不直接修改业务约定。

验证使用项目真实工具链。记录实际命令、退出结果、日志或文件位置、执行时间和关联行为 ID；未执行、失败、阻塞不能写成通过。不使用模拟数据证明业务实现正确。测试通过不证明需求正确，也不证明没有未覆盖风险。

在实现变更后，重新执行受影响验证；保留旧证据但标记过期。绑定证据的代码状态应覆盖相关工作区内容，不能只用 HEAD 代表未提交改动。仅报告脚本真实支持的版本检测能力；无法确定时手工标记待验证。

## 审查页面与接受

每阶段更新 task.json 并重新 render。用现状、计划、实际实现和证据分别说明，不为美观编造截图、指标或绿色状态。提供“自上次变化”摘要。发布前检查生成无错误；有浏览器时检查页面交互和窄屏，无浏览器时说明未做视觉检查。

HTML 中的勾选和反馈属于本地草稿，不能直接成为仓库审批或触发命令。导出后由人明确发回会话，再将决定记录到任务；保留来源和时间，不从页面点击推断授权。页面不自动发布、不自动部署、不自动提交 Git、不读取凭据。报告可能含内部路径和业务信息，分享前按项目要求检查内容。

最终交付：报告链接、重要行为变化、实际验证结果、剩余风险及下一步。不要声称正式上线或用户验收已完成，除非有真实证据。

## 团队与运维扩展
必须继续读取同目录 team-workflow.md 和 schema-reference.md。九种任务类型包含 incident 与 operations；design 为模糊需求提供合理候选方案，intake 处理跨人接手。固定模板分别呈现角色、假设、方案、交接、变更时间线及生产操作卡，禁止临时另造页面。

## 阶段专用模板（必须）
读取同目录 stage-templates.md。按 templates/stages.json 填写 stage_details，只通过内置 render 生成 HTML，不允许 AI 针对单个任务改样式、另造表格字段或脚本。新任务 init 自带完整骨架，旧任务缺失区块按目录补齐。阶段工作台是主审阅入口，原九个栏目提供详情。

## 跨项目功能
同一功能涉及多个项目时，改用 cross-project.md 的整体设计流程；feature.json 是功能总方案，task.json 是各项目实施材料。人员可以一人或多人，不以人员数量决定项目边界。
