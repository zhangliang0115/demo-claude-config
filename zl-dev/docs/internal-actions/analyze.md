# 内部动作：analyze

只在用户要理解现有业务逻辑、追踪数据来源/转换且未要求改变行为时使用。它不是新用户命令，也不要求每个含“分析”的开发请求都改成 analysis。沿用已加载的 entry-workflow.md；需要字段及来源工具时才读 analysis-workflow.md。

1. 确认要回答的问题、入口和用户允许读取的项目范围。短问题可直接引用源码文字答复，不为产物新建任务。持续分析使用 kind=analysis，mode=business_logic 或 data_flow；新建仍用 --no-render，按会话协议关联真实任务。
2. 从用户给出的页面、接口、方法、字段、表、消息或定时任务开始，沿真实调用和赋值追踪，记录条件、异常、转换、过滤、持久化、缓存及异步边界。只读取相关材料，不扫描个人目录或全部插件源码。
3. 分析可跨多个已明确项目：额外路径写 analysis.project_paths，来源标各自真实根路径。只读追踪不创建 feature 实施分工，不要求共享契约确认或 preflight。找不到的环节列断点，不凭目录名或同名字段接线。
4. 先实际读取文件，再用 analysis.py source 取得来源元数据，原样保存输出的真实 SHA256 和行号。steps/rules/mappings 与 fact 都引用来源 ID；推断写 inference，未确认写 unknown。哈希只核对版本，不证明解释正确。不能手编哈希、伪造 source.current 或把旧来源自动改绑当前。
5. 可在允许范围继续查的断点标 investigate 并继续追踪，不把写 gap 当作停工出口。确实缺少资料时标 needs_input，只询问具体缺失文件/项目/规则；明确超出本轮范围的标 out_of_scope，并限制结论。未知项若影响问题也要说明如何继续，不笼统要求人全面核验。
6. 不修改业务代码、配置、数据库或外部系统；不启动业务服务、不运行项目测试、不调用业务 API。通用 verify 对 analysis 任务会拒绝执行。需要运行验证或修复时先说明新的目标/范围，按明确请求进入合适任务，不能把纯分析静默转为实现。发现缺陷照实解释及给出建议，不擅自修复。
7. 必要事实仍通过 locate → 临时完整 JSON → CAS update 保存。结论需能回答原问题，并区分静态依据与运行未知；“材料已整理”不等于业务正确、链路跑通或验收通过。已有任务不自动转类型或改证据；明确转换应保留历史并重新整理来源。
8. 只有复杂材料确需审阅、交接或用户明确要求时 render；简单答复和中间调查不生成 HTML。需要页面时使用内置分析专页，不能自行写网站、业务请求、测试或审批表。最终返回本轮结论、关键来源、断点及适用范围，生成或复用报告时才附真实链接。
