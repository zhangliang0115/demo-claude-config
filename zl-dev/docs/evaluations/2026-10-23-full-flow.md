## 结论

一次流程演练已跑完，但插件未通过全流程验收。真实启动 Claude Code、读取两个仓库、实现接口与网页、运行 HTTP/浏览器/数据库检查、通过系统剪贴板回传报告反馈、修复真实发现的问题，并完成本地服务恢复。所有六次 CLI 调用均正常结束；正常结束不代表每项约束通过。

## 环境与业务

- Claude Code 2.1.309，实际模型 opendesign/deepseek-v4.1-flash[1m]，沿用本机配置，不代表原生 Claude 或多模型测试。
- 两个独立 Git 仓库：api（Python HTTP + SQLite）和 web（HTML/JS），各自有真实基线代码、数据库与本地进程；不是只有 task.json 的展示样例。
- 基线可以查看本人订单，没有取消能力。有本人新/旧未支付订单、本人已支付订单与他人订单，初始单商品库存 10。
- 初始输入故意模糊：“用户经常误下单，老找客服处理很麻烦，想让他自己处理一下”。要求先读项目、整体设计、不先改业务代码。
- 本地身份 X-User-ID 是测试注入，不能作为生产认证。没有生产数据、真实支付服务、外部业务系统或真实业务人员参与。

## 测试证据的边界

HTTP/SQLite 的付款竞争检查，是取消请求与条件付款数据库更新竞争，不是真实支付链路。网页成功路径使用相同页面代码与真实 API/临时数据库，通过 CDP 改写测试 API 地址；没有用假响应代替服务端。故障分支包含真实 401/404/409/500/503，以及受控断网和响应丢失注入。脚本断言数是这次案例的覆盖点，不能当作所有业务场景的覆盖率。

首版浏览器脚本曾错误地把故意触发的 HTTP/断网日志算作意外错误，后按明确状态和 URL 修正过滤再跑；原始会话保留修改记录。最终全绿仍未发现响应丢失语义错误，该问题由控制器独立故障注入发现，证明只看实现者测试结果不够。

## 未解决的插件问题

1. **只读入口会改文件。** status 技能引导调用 reviewable.py continue，而 continue 会 render。实际只读请求中 report.html 的哈希变化，task.json 未变化。应提供真正只读的定位命令，状态查询不重新生成报告。
2. **跨项目页面不跟当前阶段。** phase=design/acceptance 仍默认 discovery；页头读取 f.goal，实际目标在 f.design.goal，可能显示“尚未记录”。设计页没有可填写复制的反馈入口。
3. **契约没有实施前约束。** API 源码先写，总契约后来才升版；目前依赖模型遵循文字。需要在写业务代码前核对共同契约与版本，并留下不可混淆的变更记录。
4. **历史证据与当前阻塞混淆。** E1–E3 正确保留为过期，E4–E6 当前通过且覆盖全部行为，但汇总仍因历史 stale 记为验证缺口。模型还直接改派生快照的 issues，进一步导致快照不一致。应区分历史与当前有效证据，并让快照只能由脚本计算。
5. **默认产出目录受权限阻拦。** 运维会话对 ~/.claude 下任务文件的 Write 和 cp 被拒绝，最终降级到工作区显式目录；标准目录只留下骨架。恢复服务成功不代表产出目录要求通过。需要明确可审计、经校验的任务更新入口，不能依赖模型临时绕路。
6. **接手包有陈旧说明。** 已恢复的进程仍被接手包描述为旧代码；新会话通过独立核查纠正。本轮接收方识别了差异，仍需减少过期交接材料。

本轮只修复了测试业务项目中的“响应丢失误报未取消”缺陷；上述插件问题尚未修复。不能把这次跑完解释为插件已经可靠或已完成真实业务验收。
