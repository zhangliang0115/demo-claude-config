# 证据失效解释（0.23.0）

这次解决“旧验证为何不能作为当前依据”，不改变全仓指纹、执行来源、行为覆盖、接受和发布规则。历史记录失效与当前还有验证缺口是两件事；已有新证据覆盖的行为不因旧记录单独重跑。

## 人与 AI 如何用

仍只用 go/status。例如：

```text
/zl-dev:go 只看当前任务记录，说明旧验证为什么失效、还缺哪些检查；不要重跑测试。
/zl-dev:status 看当前任务哪些证据仍适用。
```

Agent 先用短查询协议的 locate 获取脚本推导结果，解释原因、原关联行为和当前 verification/primary_action。只有要求新调查、证明某项测试不受影响或执行验证，才进入完整工作流。需要报告时按需生成；普通解释不强制产出 HTML。

离线报告在相关证据下显示“这条记录为何不能直接作为当前依据”，展示原因、原关联行为、条件式核对建议；变更路径折叠展示。需求开发、缺陷、运维、事件和工程调整使用同一诊断组件。没有输入框、业务接口或自动测试按钮；HTML 只是生成时快照。

## 数据从哪里来

```text
verify 同一次源码扫描
  ├─ 原综合指纹：HEAD + 原行为约定 + 原路径/类型/内容字节
  └─ 分项观察：HEAD / 约定摘要 / 观察集合摘要 / 有界路径摘要
       ↓ 写入原始执行回执 fingerprint_context（可选字段）
locate/status/render
  → 核对原回执哈希、身份、日志与解析结果
  → 对比当前同规则扫描
  → 推导 freshness_details
  → 返回紧凑诊断 / 按需嵌入 HTML
```

完整分项基线只保存在新验证回执，不附加到 task.json、快照、模型摘要或 HTML。每条基线最多保存1000个路径，明细预算1MiB；总观察数量及集合摘要仍覆盖本次原规则的完整观察集合。路径是元数据，包含本地项目位置，应按原回执的私有材料管理。

locate.evidence_freshness 只返回非 current 诊断，优先无效回执，最多5条；数量和截断明确标记。每条最多展示10个变更路径。不增加对外用户命令，不为每条证据重新扫描整个项目。

## 能解释和不能解释的边界

| 情况 | 诊断 | 不能据此推断 |
| --- | --- | --- |
| 新回执有基线，HEAD变化 | head_changed | 文件看似相同就可沿用旧验证 |
| 本任务范围、行为、验收等语义约定变化 | contract_changed | 已实现或已通过新规则 |
| Git 非忽略观察集合、类型或内容变化 | source_changed，展示路径 | 谁改的、是否来自其他任务、业务行为必然受影响或无影响 |
| 原始回执或日志核对失败 | invalid_receipt，优先显示 | 代码版本匹配就能相信执行结果 |
| 旧版回执无分项基线 | legacy_missing / unknown_change | 从旧综合哈希、时间或当前 diff 反推当时变更 |
| 观察明细截断 | 部分样本，数量可能未知 | 样本中消失的路径实际被删除、列表是完整影响面 |
| 无当前代码可核对或证据未绑定 | unknown / unbound | 当前结果有效 |

“进入/移出观察集合”不等于物理新建/删除，可能涉及忽略规则变化。符号链接按原规则观察链接目标字符串，不读取外部目标内容。Git 忽略文件、外部依赖、运行环境和子模块内部内容不由此保证。变更归属始终 unknown，依赖判断仍是 whole_repository_conservative。

路径不同不能证明测试互不影响。本轮没有建设依赖图、安全减少重验范围或跨任务作者归因；这些仍属于 ZL-13 未完成部分。

## 兼容与升级

原综合指纹字节算法不变，新旧回执均兼容。可选基线损坏只降级解释，不放宽原回执与证据规则；调用者填写的派生诊断会被清除重算。匹配指纹也不把模型声明变成真实执行。

升级增加派生诊断，可能使已有报告或交接包的评估版本过期，需要页面时再生成；这不等于业务代码变化，不修改 task.json，不单因解释升级使原业务验证或接受失效，更不要求重复人工确认。旧记录没有基线时保持未知，不补造历史基线或重绑旧证据。
