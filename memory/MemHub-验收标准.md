## 1. 验收结论怎么判

**只有“功能正确、数据可靠、显式审批流程有效、仅配置端点外发、宿主不被阻塞、质量指标达标”同时成立，才能认定 v1 通过。** 能启动、能生成几条记忆或演示一次成功，都不能替代完整验收。

验收分三道技术门槛，另加一项早期收益决策 G1-V：

| 门槛 | 对应工作包 | 必须交付的证据 | 通过后允许做什么 |
|---|---|---|---|
| G0 可行性通过 | T01–T02 探针；完整 Core/schema 在 G0 后 | 环境清单、版本锁、免费 API 模型样例、真实宿主 Hook 探针、中文检索结果、数据契约、操作授权表 | 继续主体开发；不代表产品可用 |
| G1 CLI MVP 通过 | T03–T08 | 采集、抽取、审批、召回、撤回闭环；对应故障与质量测试通过 | 在一个授权项目试用 CLI MVP |
| G1-V 早期收益 | G1 后、T09 前，T11 早期子项；先具备最小备份/保守恢复 | 至少 5 对真实任务，遵守情况、审阅/修错/等待/重复解释总时间；AC-51 | 决定是否投入 Web/扩展运维，不代替 G2 |
| G2 完整 v1 通过 | T09–T11 | 全部必验用例、Web E2E、性能、质量、恢复演练和试点记录通过 | 交付当前明确支持的平台与版本组合 |

判定规则：

- 必验用例必须全部 PASS；FAIL、BLOCKED、NOT_RUN 都不能计为通过。
- 文中标记“可选”的自动启动功能，若不交付，可记 N/A 并说明范围；其余必验项不能用 N/A 跳过。
- CLI MVP 可以暂不提供 Web，但必须明确称为 CLI MVP，不能据此签收完整 v1。
- 不适用或替换方案必须有记录及负责人确认；不能在看到测试失败后直接降低指标。
- 修复失败项后，保留原失败记录，重跑该项、相关回归及主闭环；不能只保留最好的一次结果。
- 本规范进一步明确测量口径，不扩展到跨工具、多用户、Windows 或向量检索。

**一票否决项：**未完成显式确认流程的记忆生效、模型疑似冲突自行停用已批准规则、跨项目内容泄漏、撤回记忆自动复活、证据错配、修改宿主源文件、访问未配置端点或静默切换模型、密钥泄漏、无声丢弃已接受数据、持续阻塞 Claude Code。出现任一项，停止注入并阻断当前版本发布；平均正确率再高也不能抵消。

**审批边界：** 当前 v1 验证内置自动管线不批准、缺失/无效确认不生效；TTY/Web 仅为操作者声明 `operator_attested`，不能鉴别人或可控制 PTY/浏览器的同账号 Agent。测试必须如实记录后者可完成交互的能力，不能以拒绝 pipe 等价证明“Agent 无法批准”。若部署要求独立真人认证，本 v1 对该要求记 UNSUPPORTED 并不准以当前方案上线；不把此局限藏在 AC 的 PASS 中。

## 2. 环境、样本与记录要求

### 2.1 冻结运行环境

正式验收前填写并保存：

| 字段 | 必须记录的内容 |
|---|---|
| 机器 | Mac 型号、CPU 架构、内存、macOS 版本、可用磁盘 |
| 应用 | commit 或制品哈希、构建方式、配置哈希、schema version |
| 依赖 | Node 补丁版本、SQLite/绑定版本、FTS5 可用性、lockfile 哈希 |
| 宿主 | Claude Code 版本、实际宿主模型、Hook 配置及启用范围 |
| 抽取 | 免费 API 平台、端点主机、模型 ID、上下文上限、生成参数、当日额度与限流配置、服务条款/数据政策版本 |
| 数据外发 | 脱敏规则版本、发送字段白名单、`--show-request` 预览记录、密钥存放位置 |
| 管线 | parser version、pipeline version、Stage A/B 提示词哈希 |
| 测试 | 数据集版本、样本清单及哈希、测试运行 ID、执行人与日期 |
| 运行上限 | 读取/记录大小、轮询周期、租约、重试、每日批次/请求/token、每批全流程预算、等待上限、maxAutoReviewMemories、磁盘和日志限制 |
| 审批与范围 | operator_attested 边界、确认入口及反重放；project/paths/unknown 语义；启动仅全项目规则 |
| 隔离与恢复 | 单项目 dataDir、备份 project ID、authorizationEpoch/runtimeEpoch/memoryGeneration、恢复屏障状态 |

模型 ID、端点主机、提示词或 parser 变更，必须视作新验收配置并重新验证。免费平台限流、额度或服务条款变化时，也要记录并评估影响；不能静默更换模型后沿用旧结果。仅界面文案修改可按影响范围回归，但需留下理由。

### 2.2 隔离测试数据

使用独立测试数据目录和两个合成项目 A/B，A 的 dataDir 只授权 A。一个 dataDir 不得登记第二项目；需要 B 自身状态的测试另用 B 的 dataDir，不能与 A 共享库或备份。故障注入、数据库损坏、磁盘限额和删除演练都在此目录进行，不使用用户唯一一份真实历史。

样本分为三组：

1. **确定性工程 fixtures**：有精确记录 ID、内容块数、作者、字节边界、预期游标和状态，用于验证采集与事务。
2. **记忆质量集**：至少 100 个样例，30 个开发、20 个验证、50 个冻结验收；同会话及近重复片段不能跨集合。
3. **性能集**：100 个合成或授权脱敏会话、1,000 条记忆；固定文件大小分布、正文长度及状态比例，保留生成种子或数据哈希。涉及免费 API 抽取时，使用预录的合法模型响应或受控模拟服务，避免额度波动使测量不可重复；真实 API 另跑端到端确认。1,000 条是本地搜索性能基线，不表示生产自动审查支持此规模；超过 maxAutoReviewMemories 的真实模型规模实验仅在隔离 G0 探针中显式运行。

质量集的每条标签必须包含：应记事实、类型、范围、有效时间是否明确、证据 ID/片段、禁止推断内容。负例明确标注“不应记忆”。标签在模型正式运行前完成。

### 2.3 证据与结果目录

建议每轮验收保存为 `acceptance/<run_id>/`，包含以下文件；这是拟建目录，本次不生成测试结果。

| 文件 | 内容 |
|---|---|
| `manifest.json` | 上述环境、版本、数据集和配置 |
| `cases.csv` | 用例 ID、状态、实际结果、证据路径、缺陷 ID、执行人 |
| `tests/` | 单元/集成/E2E 报告及覆盖率 |
| `state/` | 脱敏数据库状态摘要、游标、任务与 revision 对比 |
| `quality/` | 全量预测、人工评分、分子分母、失败样例 |
| `performance/` | 每次测量原始耗时、内存、失败与超时，不仅是均值 |
| `host/` | Hook 输入/输出、生命周期事件、会话行为证据 |
| `network/` | 测试进程、出站规则、连接/请求观测记录 |
| `decision.md` | 通过范围、未解决问题、签收结论 |

证据默认脱敏，保留在本机。截图用于补充 UI 证据，不能替代数据库状态、请求计数或测试断言。

## 3. 主闭环验收：用户能否少解释一次

**AC-01，必验；关联 T04–T08、T11。**

前置：新建项目 A，库为空，已配置且获同意的免费 API 模型可用；测试项目没有通过 CLAUDE.md、原生 memory 或其他插件保存下列规则。

| 顺序 | 操作 | 必须观察到的结果 |
|---|---|---|
| 1 | 在会话 A 明确说“此项目以后不使用 ORM，数据库查询使用手写 SQL”，完成该轮对话 | 形成属于项目 A 的证据，作者为 person |
| 2 | 等待 flush 或手工触发提取 | 出现 `constraint` 候选；逐字证据和来源可查看；尚未 active |
| 3 | 执行上下文预览及默认搜索 | 未批准候选不出现在有效记忆结果或注入内容中；审阅页可查看 |
| 4 | 人工批准该具体 revision | 生成批准事件；记忆成为 active，带稳定 ID、revision 和证据关联 |
| 5 | 安装注入，开启独立会话 B，要求实现一个数据库查询，不重述该规则 | Hook 返回完整约束短句；宿主产出的实现遵守手写 SQL 约束 |
| 6 | 查看记忆详情 | 能从注入 ID 追溯到步骤 1 的证据，而非 Agent 的转述 |
| 7 | 撤回该记忆，再执行预览、搜索和新会话启动 | 撤回事务提交后的新读取均不将其作为有效记忆返回；界面说明旧会话内容无法被收回 |
| 8 | 重启服务、重扫历史并重试原任务 | 该规则不会自动复活或重新生效 |

通过标准：八步全部满足。步骤 5 是单个闭环演示；整体行为可靠性仍须满足第 6 节的配对任务门槛。撤回后的宿主仍选择手写 SQL 不构成失败，撤回验收检查“是否仍注入该记忆”，不能用模型是否反向行动判断。

保留证据：完整操作日志、候选/批准/撤回状态、证据关联、Hook 输出、会话 B 的实际产物和重扫前后对比。

## 4. 功能与数据正确性验收

所有表格行均为必验项。一行有多个分支时，每个分支分别记录结果。

### 4.1 授权与采集（T03、T04）

| ID | 前置与操作 | 通过标准 | 必留证据 |
|---|---|---|---|
| AC-02 | A/B 各放入可识别的不同规则；仅授权 A，启动扫描、监听和补扫；尝试在请求中指定 B | B 的正文不落业务库、不进入模型请求或召回；伪造项目 ID 被拒绝 | 授权配置、请求记录、数据库查询 |
| AC-03 | A 中配置指向 B 的符号链接；准备工作目录不明、多仓库、移动后来源 | 未授权路径拒绝；归属不明记录隔离，不自动并入 A | 路径校验结果、原因码 |
| AC-04 | 固定同一管线版本，完成一次导入和抽取；再导入同一文件两次 | 第二、三次新增证据版本、候选、有效记忆均为 0 | 三轮对象计数和 ID 对比 |
| AC-05 | 同会话放入两条宿主 ID 不同、文本均为“继续”的记录；再重扫 | 保留两个独立事件；重扫不会变为一个或四个 | 事件 ID、源记录 ID |
| AC-06 | 同一 user 记录混合普通文本和 tool_result；加入 assistant、host、unknown、子代理记录 | 按块拆分；作者与角色正确；子代理不进入主会话，跳过有原因 | 预期块清单与解析结果 |
| AC-07 | 分两次写入一条 JSONL，第一次不含末尾换行；中间扫描两次 | 半行不被当作永久坏行，已提交 offset 不越过半行；补齐后恰好导入一次 | 每次 offset、账本和消息数 |
| AC-08 | 分别执行截断、轮转、同 inode 等长覆盖、只覆盖已读前缀；加入缺宿主 ID 的重写案例 | 触发重扫/代次更新或明确隔离；不把重放当新事实、不误合并独立事件；定期指纹扫描可发现前缀变化 | 文件指纹、generation、对账结果 |
| AC-09 | 导入合法跳过、坏 JSON、未知类型、可拆多块等混合文件 | 每条完整记录恰有一个处理结果；记录总数与分类总数相等；消息数另计 | 固定 fixture 预期与处理账本 |
| AC-10 | 导入总大小 >32 MiB 的文件、超过单记录上限的记录，以及其后的正常记录 | 大文件分轮完成；超限记录有字节区间和原因；后续记录仍可读；无单次全文件装入内存 | 读取批次、内存曲线、offset |
| AC-11 | 临时丢弃文件通知后追加内容，保持服务运行 | 在一个补扫周期加 T01 冻结的处理裕量内发现；无丢失和重复。默认周期为 30 秒 | 追加时间、发现时间和 ID |

### 4.2 Turn、任务与失败恢复（T05、T06）

| ID | 前置与操作 | 通过标准 | 必留证据 |
|---|---|---|---|
| AC-12 | 分别输入未回答提问、仅工具调用、完整回答；快进空闲时钟；再补迟到结果 | 未答与仅工具调用不被误作完整事实；空闲不宣称会话结束；迟到数据有新 revision | turn 状态和任务输入 |
| AC-13 | 分别累计 5 个完整 turn、让少量完整 turn 等待 5 分钟、执行手工 flush；另输入 >20 个 turn | 三种触发均有效；同一批不重复入队；每批 ≤20 个 turn 且满足输入预算 | 时钟、job 输入及范围 |
| AC-14 | 输入超过模型上下文的内容，在末尾放置检查标记 | 安全分批/分窗并报告覆盖范围，或显式阻塞供人工处理；不静默丢尾部 | 模型请求大小、覆盖账本 |
| AC-15 | 在证据提交前后、模型返回后、候选提交与任务完成边界分别强制终止进程 | 每个故障点至少重复 3 次；恢复后游标、证据、候选一致，无重复有效结果 | 故障点、恢复状态、事务断言 |
| AC-16 | 同时启动两个 Core；让一个任务租约过期，再提交旧 worker 结果 | 至多一个业务写入者；旧租约结果不能覆盖新状态；最终最多一个逻辑提交 | 锁、租约、任务与结果 ID |
| AC-17 | 免费 API 未配置、不可达、模型下线或额度耗尽；恢复服务 | 明确 blocked/失败及原因；数据和未处理位置保留；不自动切换其他平台；恢复后能续跑 | 状态变化、请求计数、剩余额度 |
| AC-18 | 模型模拟器分别返回超时/5xx、429、401/403、配额耗尽 | 网络类含首次最多 3 次；429 尊重重试时间；认证/配额错误停止对应队列，无逐 job 重试风暴 | 请求时间序列、attempt 和原因码 |
| AC-19 | 模拟器返回坏 JSON、非法枚举、越界长度、错项目证据 ID、伪造引文；另返回合法空数组 | 非法结果不能进入可批准候选；格式修复最多 1 次，仍失败可恢复；空数组记正常完成，不混为错误 | 原因码、调用次数、候选查询 |
| AC-20 | 降低测试预算/磁盘限额至可触发值；耗尽后继续添加数据 | 停止相关写入或模型任务，保存未处理位置；不推进未提交游标、不无限重试；解除限制后恢复 | 上限配置、游标、队列变化 |

故障模拟器只用于验证边界逻辑；真实免费 API 模型抽取与质量验收必须另跑，不得用模拟结果代替。免费平台可能排队或限流，AC-18 的重试与 AC-20 的预算验收要记录实际等待时间，不能只记录最终成功。

### 4.3 证据、审批与遗忘（T06、T07）

| ID | 前置与操作 | 通过标准 | 必留证据 |
|---|---|---|---|
| AC-21 | 构造 ID 确实存在但不支持候选结论的证据；检查 Stage B 输入 | 审查能读到证据、作者及必要前后文；错误候选被拒绝或退回，不能仅因 ID 存在获得有效证明 | Stage B 脱敏输入及裁决 |
| AC-22 | 创建 pending、rejected、active、superseded、revoked、needs_review 各状态 | 默认 search/show 仅提供当前有效 active，保留范围条件；Hook 进一步只选择 project 范围；历史/审阅视图明确标状态 | 各读取入口输出 |
| AC-23 | 提出 merge/supersede，批准前后各查询一次；中途制造事务失败 | 批准前旧有效版本不被原地改写；批准后新旧状态原子切换；失败不留半更新 | revision、审计、FTS 对比 |
| AC-24 | 构造同范围疑似矛盾及不同范围表面矛盾；模型提出冲突后，操作者再确认/解决冲突 | 模型结果仅 suspected、不改变旧 active；交互确认 confirmed_unresolved 才暂停相关规则；裁决后仅合格版本生效，不同范围不盲目替代 | 确认前后冲突关系、范围、治理版本及注入结果 |
| AC-25 | 两个审阅窗口加载相同 revision；先修改，再从旧窗口批准 | 旧 revision 操作被拒绝，要求刷新；不得覆盖已提交更改 | 请求版本和响应 |
| AC-26 | 模型调用期间修改/删除证据、撤销项目授权或替换目标 revision | 证据/授权变化令旧输入失效；仅有效集合变化时保留有效 Stage A、在预算内重做 Stage B，旧裁决不提交 | authorizationEpoch/runtimeEpoch/memoryGeneration、证据/治理版本、任务状态 |
| AC-27 | 拒绝或撤回后，依次重启、重扫、重试和升级提示词重抽；再加入新的明确证据 | 原证据不能使记忆自动复活；新证据最多形成待审候选，显示既有撤回历史 | 抑制记录、候选及 active 计数 |
| AC-28 | 一条记忆关联多条证据，依次删除部分及全部支持证据 | 支持不足时转 needs_review，不继续注入；不存在悬空关联；手工录入不能冒充 transcript 证据 | 关联表、状态和来源标记 |

### 4.4 检索、注入与安装（T08）

### 5.2 性能测量口径

基准固定为同一台登记 Mac、100 个会话、1,000 条记忆。测量开启实际治理过滤与日志，不使用与生产不同的捷径。

| 项目 | 测量方法 | 通过门槛 |
|---|---|---|
| 本地搜索 | 固定查询顺序，预热 10 次，再测 200 次；从 CLI 启动计时至完整结果输出 | p95 ≤200 ms；失败与超时单列，不能从样本中删掉 |
| Hook | 新进程执行 200 次，数据页已预热；从启动进程计时至输出完成 | p95 ≤300 ms；业务逻辑从入口起 500 ms 内停止查询/渲染，无模型调用 |
| Hook 故障截止 | 用受控阻塞测试，记录宿主显式 timeout | 在配置上限内结束/取消并允许宿主继续；timeout 数值在 T01 固定，不能使用无限等待 |
| 冷启动 | Core/模型重启后的首个搜索、Hook、抽取分别测 10 轮；说明 OS 文件缓存是否保留 | 报告全部样本、最大值和失败；Hook 仍遵守截止与降级，不冒充热态 p95 |

p95 采用 nearest-rank：对 n 个耗时升序排列，取第 `ceil(0.95 × n)` 个；n=200 时取第 190 个。测量期间记录并发负载。不能用平均值代替 p95，也不能只测内部 SQL 而排除 CLI 启动成本。

## 6. 抽取质量与实际收益门槛

### 6.1 计分口径

质量评测针对 **Stage B 后、人工批准前** 的最终保留候选。人工审批不能把模型误报先删掉，再宣称抽取 precision 很高。Stage A 原始候选和 Stage B 丢弃项同时保存，供定位错误。

在每个冻结样例中做一对一事实匹配，事实、作用域、否定含义和证据必须正确，文字可以不同。设：

- `C`：全部最终保留候选数，包括错误、重复和噪声候选。
- `TP`：一对一匹配到标签事实的正确候选数，同一目标事实最多记一次。
- `E`：标签中应抽出的 constraint/convention 事实数；`TP_cc` 为被正确匹配的这两类事实数。
- `N`：属于明确禁止抽取类型的候选数。
- `D`：重复于当前已有效记忆或本批另一候选、且没有新增有效信息却仍作为新条目保留的候选数。合法补证据 merge 不计重复。

| 指标 | 公式 | 通过门槛 |
|---|---|---|
| Precision | TP / C | ≥90% |
| 约束/约定 Recall | TP_cc / E | ≥80% |
| 噪声率 | N / C | ≤5% |
| 重复率 | D / C | ≤5% |
| 已批准记忆可追溯率 | 有有效引用且引文支持结论的条目 / 被检查的已批准提取记忆 | 100%，逐条检查 |
| 禁止生效事件 | 未批准、外部投毒或跨项目条目实际进入注入的次数 | 0 次 |

冻结集必须含三种支持类型和负例；E 必须大于 0。C=0 时 precision 等记 N/A，不能算 100%；若没有待检查的已批准条目，可追溯率也为 N/A，主闭环因此不能通过。手工录入单独审计来源，不混入自动抽取可追溯率分母。

在同一冻结配置上运行 3 次，固定可控的生成参数，每次均达到四项抽取质量门槛，同时报告各次分子分母和波动，不挑最好的一次。冻结验收集至少 50 个样例；结果只支持该样本范围内的结论。

验收集用于定位错误并调参后，该版本结果不能继续声称是独立验收；补充未见样例并重新冻结。评分由人工核验，有歧义时复核，不让同一个抽取模型自行宣判全部正确。

### 6.2 跨会话实际收益

先在 G1 后执行 AC-51 的 5 对早期收益判断，再决定是否开发 Web/扩展运维。下面是 G2 的独立正式验收，不能用早期小样本替代。

至少 20 个配对任务，每个任务分别跑“无助手”和“启用助手”，共至少 40 次任务执行。

要求：同一宿主模型与配置、相同任务和初始项目快照；两组都经历相同的会话 A 指令，再启动隔离的会话 B。原生 memory、其他插件和项目指令文件保持一致，禁止把助手结果复制给基线；交替或随机安排运行顺序，避免后跑的一组继承前组产物。

每个任务提前写出可观察判据，例如依赖清单是否新增 ORM、数据库列名是否符合 snake_case。不能仅凭模型说“我记住了”判成功。

通过要求：

- 启用助手的约束遵守任务至少 18/20。
- 基线未达 18/20 时，启用后的遵守数还必须高于基线。
- 基线已经达到或超过相同效果时，保持行为表现不下降，并额外测量维护/重复解释时间。计入审阅、改错、维护记忆、重复解释和关键路径等待助手的耗时；并发活动按实际墙钟区间并集计，不把后台运行与人工操作时间重复相加；中位总耗时须低于基线，保留原始记录，否则不能声称已证明实际收益。
- 记录误用历史、纠正次数、详情查询次数、注入体积及延迟；一票否决事件仍要求 0 次。

行为指标通过但收益未证明时，可以记录“技术验收通过、产品收益待验证”，不能笼统写“v1 全部验收完成”。
