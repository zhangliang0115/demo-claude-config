# 实用性审查与改进（2026-10-23）

结论：旧版更接近报告生成器，交付过程过度依赖 AI 填表，尚不能宣称是成熟的开发协作系统。

## 实际发现与处理

1. 日常要理解多个命令、任务目录和阶段：新增 go 默认入口和 continue 任务发现，下一步依据真实记录推导；不会错误地把多个任务默选为一个。
2. 首页暴露十个栏目、九阶段和重复说明：默认只看变化、最多三项决策、证据缺口和下一步；完整模板收进详情。固定样式保留，空白表格不再强制成为任务。
3. 补写测试结果会改变 stage_details 指纹，导致结果自我过期：限定语义契约，报告元数据不影响证据，行为与源码变化仍使其过期。添加回归测试。
4. 跨项目 readiness 恒为 false：改为依据项目可访问性、契约、分工、快照和真实行为证据给出联调准备状态；与交付完成分开。

## 本轮尚未解决

- HTML 反馈仍是离线草稿，不是可回写审批服务。
- stage_details 与常用字段仍兼容共存，已取消强制重复填写；尚未全部归并成一个数据模型。
- 子任务绑定仍需 AI 按协议建立，没有自动派工/同步服务。
- 真实 Claude 模型的一次完整开发任务尚未评测，不能把脚本测试当作 agent 工作质量证明。
- 没有业务运行环境时，静态演示不能证明产品可用。

## 验证方向

选择一个真实小功能，观察从描述到可运行结果期间，人需要做几次额外解释、能否从首页理解行为、是否发现隐藏假设、端到端测试是否能独立复现。不要以文档量、代理数量或字段完整率评价效果。
